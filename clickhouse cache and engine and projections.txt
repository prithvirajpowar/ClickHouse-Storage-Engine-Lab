Async Insert — Brief Explanation
What it is:

A setting in ClickHouse that changes how INSERT statements are handled on the server side. Instead of immediately writing each INSERT to disk as its own file, the server holds incoming rows in a memory buffer for a short time, then writes many small inserts together as one larger batch.
What it does, step by step:

Client sends an INSERT (even just 1 row)
Server doesn't write it to disk right away — it adds it to an in-memory buffer
Server waits briefly (controlled by async_insert_busy_timeout_ms, default ~200ms) or until the buffer reaches a size limit
Server then writes everything collected into one disk part, instead of one part per insert

Why we use it:

The core problem it solves is "too many small parts." ClickHouse is built for large, infrequent writes — not thousands of tiny ones. If many small INSERTs each create their own part, the server gets overloaded with file management (merging, indexing) and performance degrades, sometimes causing the cluster to throttle or reject inserts ("too many parts" error).
Async insert fixes this by letting the server do the batching automatically, instead of requiring the application/client to batch rows manually before sending them.
Where it matters in practice:

High-frequency, small-row ingestion — IoT sensors, application logs, event tracking, telemetry — anywhere many independent sources are each sending small amounts of data continuously, rather than one process sending large bulk loads.
One important setting to know:

wait_for_async_insert controls durability:

=1 (safe, default-recommended): client waits until the buffered data is actually flushed to disk before confirming success
=0 (faster, riskier): client gets an immediate "OK" even though data is still only in memory — if the server crashes before flushing, that acknowledged data is silently lost

Mark Cache — What It Is and Why We Use It
The problem it solves:

ClickHouse stores table data in column files on disk, sorted by your ORDER BY key (in your case, event_date, user_id). To quickly find which part of those files contains the rows you're looking for — without scanning the entire file — ClickHouse keeps small index files called "marks." Think of marks like a book's index: instead of reading every page to find a topic, you jump straight to the right page number.
What a "mark" actually is:

A mark is a small entry that says: "for this range of the primary key, the actual data starts at this byte offset in the column file." Every table has a .mrk file per column holding thousands of these entries.
The cache itself:

Reading those .mrk files from disk, every single time, for every query, is wasteful — they don't change unless the table's data structure changes. So ClickHouse keeps recently-used marks in RAM. That RAM area is the Mark Cache.
Why this matters for performance:

Without the mark cache, every query — even one that only touches a tiny slice of data — pays a "where do I look" disk-read cost before it even starts reading actual data. With the cache warm, that lookup step is skipped on repeat queries, especially valuable for dashboards or reports that get queried repeatedly with similar filters.

Uncompressed Cache

This cache is disabled by default, so we enable it explicitly first.

SET use_uncompressed_cache = 1;

SYSTEM DROP UNCOMPRESSED CACHE;

SELECT event_type, count(), sum(revenue) FROM events
WHERE event_date = today() - 5
GROUP BY event_type
SETTINGS use_uncompressed_cache = 1;

SELECT event, value FROM system.events
WHERE event IN ('UncompressedCacheHits','UncompressedCacheMisses');

Run that block first and note the result. Then run the identical query again, followed by the counter check again:

SELECT event_type, count(), sum(revenue) FROM events
WHERE event_date = today() - 5
GROUP BY event_type
SETTINGS use_uncompressed_cache = 1;

SELECT event, value FROM system.events
WHERE event IN ('UncompressedCacheHits','UncompressedCacheMisses');

Uncompressed cache is disabled by default because it trades RAM for speed in a very specific scenario — repeated access to the same small dataset. When we turned it on and ran the same query twice, the second run was 8 times faster, because the data didn't need to be decompressed again. This makes it a good fit for small, frequently-revisited datasets like recent-hours hot data or lookup tables — but not something you'd blanket-enable for an entire large analytical table, since the RAM cost would outweigh the benefit for data that's rarely re-read

Why It's OFF by Default (this is the important part)
This is the opposite tradeoff from Mark Cache. Three real reasons:
1. It's expensive in RAM, fast or not

Decompressed data is much bigger than compressed data — often 3-6x larger. Caching it means committing serious RAM to hold relatively little data. Mark cache, by comparison, caches tiny index entries — cheap to keep around. Uncompressed cache is "expensive rent for the space it takes."
2. It only helps a specific, narrow pattern

It's only worth it when: the same data gets read repeatedly, AND the working set is small enough to actually fit in RAM. Most analytical queries in ClickHouse scan large, varied ranges of data — a different slice every time — so caching "the last thing read" rarely gets reused before something else evicts it. ClickHouse's own design philosophy assumes large scans are the norm, not small repeated point-lookups, so the engine doesn't waste RAM on this by default.
3. Decompression itself is already fast

Modern compression algorithms like LZ4 are deliberately chosen for speed, not maximum compression ratio. The CPU cost of decompressing on every read is often cheaper than the complexity of maintaining a cache for it. So the "problem" this cache solves is smaller to begin with compared to Mark Cache's problem (disk seeks).
Bottom line: Mark Cache is "always a good idea, cheap to keep on." Uncompressed Cache is "situational — only worth it for specific small, hot, frequently-repeated datasets," which is exactly why ClickHouse makes you opt in explicitly rather than enabling it for everyone by default.

Then check:
SELECT event, value FROM system.events
WHERE event LIKE 'QueryConditionCache%';


Query Condition Cache makes repeated lookups on the same filter condition progressively cheaper by remembering which chunks of data are worth checking — without freezing the answer in time the way a full result cache does. Running the identical filter twice cut the amount of data scanned by more than half.

Phase 3 = Projections

Step 1 — Baseline (no projection yet)

SELECT event_type, count(), sum(revenue) FROM events
GROUP BY event_type;

Step 2 — Create the projection
ALTER TABLE events ADD PROJECTION event_type_summary (
    SELECT event_type, count() AS cnt, sum(revenue) AS total_revenue
    GROUP BY event_type
);

Step 3 — Materialize it (backfill for existing 10M+ rows)
ALTER TABLE events MATERIALIZE PROJECTION event_type_summary;

This one might take a few seconds since it's building the projection across your whole table — that's expected, not an error.

Step 4 — Confirm it actually built
SELECT table, name, part_name, rows, marks, bytes_on_disk
FROM system.projection_parts
WHERE table = 'events';


Why We Need This At All
Without a projection, every time someone runs "give me totals by event_type," ClickHouse re-reads and re-aggregates all 10 million raw rows — every single time, even though the answer to "totals by event_type" barely changes between queries if no new data has arrived. The projection means that work gets done once, automatically, as data is inserted — and every subsequent identical query reads a few hundred bytes of pre-computed summary instead of scanning megabytes of raw data.

We haven't yet confirmed ClickHouse actually uses this projection automatically. Let's check now:

SELECT event_type, count(), sum(revenue) FROM events
GROUP BY event_type;

SELECT event_type, count(), sum(revenue) FROM events
GROUP BY event_type;

Run that exact same query again, and note whether Processed rows drops dramatically from 10 million.

EXPLAIN SELECT event_type, count(), sum(revenue) FROM events
GROUP BY event_type;

BUSINESS IMPACT SUMMARY

- Faster repeated queries (Query Cache: 78x, Projections: 29x) mean dashboards
  and reports return near-instantly on repeat views -- faster decisions for
  anyone using the data.
- Caching mechanisms reduce repeated compute cost on the same hardware --
  lower infrastructure spend as query volume grows.
- Async Insert and Buffer Engine prevent ingestion-side instability under
  high-frequency small writes, protecting the system from the "too many
  parts" failure mode as data volume scales.
- All mechanisms are native to ClickHouse -- no external cache (e.g. Redis)
  required, no additional infrastructure to maintain.
